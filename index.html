01

Why digital money is hard

Physical money is simple. You hand a $20 bill to someone — they have it, you don't. It can't be in two places at once.

Digital money is not so simple. A "digital coin" is just a file. Files can be copied. If you send me a file representing $10, what stops you from sending the same file to a hundred other people? This is the double-spending problem, and it's why digital cash didn't really exist for decades.

The traditional fix: trust a bank. The bank keeps a single ledger. When you send money, the bank subtracts from your row and adds to the recipient's row. Everyone has to trust that the bank won't lie, freeze accounts, or go bankrupt.

Bitcoin's idea: skip the bank. Make the ledger public, copied across thousands of computers. Anyone can verify the rules were followed. The hard part: how do thousands of independent computers agree on what's true, with no central authority? That's what the rest of this tutorial is about.

02

Hashes — Bitcoin's fundamental tool

A hash function takes any input — a word, a file, a whole book — and produces a fixed-size fingerprint. Bitcoin uses SHA-256, which always outputs 256 bits (64 hex characters), no matter how big or small the input.

Three properties make hashes useful:

  • Deterministic. Same input always produces the same output.
  • One-way. Given a hash, you cannot reverse it to find the input. The only way to find what produced a hash is to guess inputs and try them one at a time.
  • Avalanche. Changing one bit of input completely scrambles the output. There's no "close" — every input produces a hash that looks random.
—

Change a single character. The output is completely different — there's no pattern, no partial match.

Every other Bitcoin concept is built on this. "The hash of a block." "The hash of a transaction." "Mining is finding a hash that…" — all the same SHA-256.

03

Blocks linked by hashes

A block is a bundle of transactions plus a small header. The header has six fields, but the critical one for now is previous block hash — the SHA-256 hash of the block that came before.

Block #5
prev: 0000a3f0…
txs: 4
hash: 0000b2e1…
→
Block #6
prev: 0000b2e1…
txs: 7
hash: 0000c8d4…
→
Block #7
prev: 0000c8d4…
txs: 2
hash: 0000f9a2…

This is what makes it a "block-chain". Every block contains the fingerprint of the previous one. If anyone modifies a transaction in an old block, that block's hash changes, which means the next block's "previous hash" no longer matches, which breaks every block built on top.

You can't quietly change history. Any tampering propagates forward and is immediately visible to anyone with a copy of the chain.

04

Mining is a hash lottery

Hashing a block is fast. So fast that an attacker could rewrite history by quickly recomputing all the affected hashes. Bitcoin's defense: make finding a valid block hash artificially expensive.

The rule: a block is only valid if its header's hash starts with a certain number of zeros. There's no clever shortcut. You have to keep changing one field of the header — the nonce — and rehashing, over and over, until you get lucky:

This is mining. Whoever finds a valid hash first gets to add the block to the chain and collect a reward (currently 3.125 BTC on mainnet, 50 BTC on regtest). The number of required zeros — the difficulty — adjusts automatically every 2,016 blocks so the global network produces a new block roughly every 10 minutes.

To put a number on it: as of April 2026, Bitcoin's mining difficulty is 135.59 trillion and the global network is running at about 940 EH/s — 940 × 10¹⁸ SHA-256 attempts every second. A valid block hash needs roughly 20 leading hex zeros in front. Even with that planetary amount of hashing, it still takes ~10 minutes per block. The simulator above is dialed down by about 20 orders of magnitude so your laptop can find one in milliseconds.

What does "difficulty 135.59 T" actually mean?

"T" stands for trillion. So 135.59 × 10¹² ≈ 1.36 × 10¹⁴. The number is saying: finding a valid block today is 135.59 trillion times harder than it was at Bitcoin's launch in January 2009.

The mechanism: every block header has a bits field that encodes a 256-bit number called the target. A block is only valid if its hash, interpreted as an integer, is ≤ that target. Smaller target = fewer valid hashes exist in the 256-bit space = harder to find one.

Difficulty is defined as the ratio difficulty_1_target ÷ current_target, where difficulty_1_target is a fixed protocol constant: 0x00000000ffff0000… (about 2²²⁴, encoded as bits = 0x1d00ffff). It's hardcoded into Bitcoin Core — not derived from any block. Mainnet's genesis happens to be mined at exactly this target, so genesis difficulty = 1, but that's a coincidence specific to mainnet (regtest's genesis, for example, has difficulty ~4.6 × 10⁻¹⁰).

EraDifficultyRequired leading zero bitsAvg attempts per block
Genesis (Jan 2009)1~32 (≈ 8 hex zeros)~4.3 × 10⁹
Today (Apr 2026)135.59 × 10¹²~79 (≈ 20 hex zeros)~5.8 × 10²³

So a real mainnet block hash today looks like:

00000000000000000001a3f7c8e2b9d4...
└──── ~20 leading hex zeros ─────┘

The number gets recomputed every 2,016 blocks (~2 weeks). The protocol checks: "Did the last 2,016 blocks take more or less than 20,160 minutes (= 10 min × 2,016)?" If faster, difficulty goes up; slower, it goes down. Capped at 4× change per period in either direction. There's no committee, no vote — just three lines of arithmetic in pow.cpp of Bitcoin Core.

Historical climb: 2009: 1 · 2013: 50 M · 2017: 1 T · 2021: 25 T · 2024: 80 T · 2026: 135.59 T. Each jump tracks the global investment in faster ASIC mining chips — more hashpower joins, blocks come too fast, the next retarget tightens the target.

This is also why the chain is tamper-resistant. To rewrite block #100, an attacker doesn't just have to redo block #100's mining — they have to redo blocks #100, #101, #102, … all the way up to the current tip, faster than the rest of the network produces fresh blocks. That requires more hashing power than the rest of the planet combined. In practice: not affordable.

05

Keys and addresses — how ownership actually works

Bitcoin doesn't store who owns coins. There's no "Alice owns 5 BTC" anywhere in the protocol. Instead, it stores locks — each coin output is locked to a specific cryptographic puzzle, and "ownership" simply means knowing the secret that solves the puzzle.

The puzzle is built from three layers:

  • Private key. A randomly chosen 256-bit number. That's it — just a random number. The space of possible private keys is ~10⁷⁷, which is more than the number of atoms in the visible universe. If you can pick one that nobody else has guessed, the coins locked to it are effectively yours.
  • Public key. Derived from the private key using elliptic curve math (specifically the secp256k1 curve). The math is one-way: trivial to compute public from private, computationally infeasible to reverse.
  • Address. A hash of the public key, then encoded into a human-friendly string (bech32 for the modern bc1q… / bcrt1q… formats). Hashing the public key is a small extra privacy step — the actual public key only gets revealed when you spend.
What does this look like with real numbers?

A real Bitcoin keypair (do not use this — it's a published example):

private key:   18e14a7b6a307f426a94f8114701e7c8e774e7f9a47e2c2035db29a206321725
public key:    0250863ad64a87ae8a2fe83c1af1a8403cb53f53e486d8511dad8a04887e5b2352
address:       bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4

The private key is just 64 hex characters (256 bits). The public key is computed by elliptic-curve point multiplication: pubkey = privkey × G where G is a fixed "generator point" defined by secp256k1. The address is bech32(ripemd160(sha256(pubkey))) with a "bc1" human-readable prefix.

The simulator generates fake addresses by picking random characters from the bech32 alphabet — they look real but have no underlying key. A real address always has a valid checksum and a real key behind it.

Here's the part that's worth pausing on. When you "send" bitcoin, you don't tell the network "transfer X to Y." You construct a transaction and sign it with your private key. The signature is a number computed from (a) your private key and (b) the exact bytes of the transaction. Anyone can verify: "this signature could only have been produced by the private key matching this public key, for this exact transaction." The verification uses the public key — your private key never leaves your machine.

That's the magic trick: the signature proves authorization without revealing the secret. This is what "trustless" means. No bank, no notary, no custodian needs to vouch for you. The math vouches for itself. Anyone running a Bitcoin node can verify every signature in every transaction in the entire chain, without ever knowing who you are.

The flip side: if you lose your private key, the coins it locked are unrecoverable. If someone else gets it, they can spend your coins. There's no password reset. No customer service. This is the part of Bitcoin that makes self-custody both genuinely powerful and genuinely demanding — most users delegate this to a wallet app, a hardware device, or a custodial exchange that holds the keys for them.

🔑
The simulator's Wallet tab handwaves all this — addresses are random strings with no keys, sends always succeed. In real Bitcoin, every send requires a valid signature against the UTXO being spent (next chapter).
06

UTXOs — what's actually being spent

Most people picture Bitcoin like a bank account: "Alice's balance is 5 BTC." That mental model is wrong, and it's worth fixing because the actual model affects everything from fees to privacy to how you build wallet software.

Bitcoin has no concept of an account or a balance. It tracks unspent transaction outputs — UTXOs. Each UTXO is a discrete chunk of bitcoin, locked to an address (or more precisely, to a script — see chapter 5), created by some previous transaction. Your "balance" in any wallet is just the sum of UTXOs that wallet can sign for.

Picture it like cash in a wallet:

Alice's UTXOs:
  └─ 0.5 BTC   (received from tx abc123…, output #0)
  └─ 1.2 BTC   (received from tx def456…, output #1)
  └─ 0.8 BTC   (mined coinbase from block #91, output #0)
─────────────
  Balance: 2.5 BTC  (the wallet's UI just sums them)

When Alice sends 1 BTC to Bob, here's what actually happens at the protocol level:

  1. The wallet picks one or more UTXOs whose total ≥ 1 BTC + fee. Say it picks the 1.2 BTC UTXO.
  2. It builds a transaction that consumes that entire UTXO as an input (UTXOs can't be partially spent — they're consumed whole).
  3. It creates new outputs: 1 BTC to Bob's address, plus 0.198 BTC change back to Alice (typically to a fresh address she controls), plus 0.002 BTC implicit fee (the difference between input total and output total goes to whoever mines the block).
  4. Once mined, the 1.2 BTC UTXO is gone from the global UTXO set. Two new UTXOs exist in its place: one for Bob, one for Alice.
Before:                        After:
  Alice: 1.2 BTC UTXO     →     Bob:   1.0 BTC UTXO  (new)
                                Alice: 0.198 BTC UTXO (change, new)
                                Miner: 0.002 BTC fee (in their coinbase)
Why design it this way? Why not just have account balances?

No global state to mutate. Each UTXO is independently spendable. Verifying a transaction is "do these inputs exist in the UTXO set, do the signatures check out, do the output amounts add up to ≤ input amounts?" — purely local. No need to look up account balances or worry about ordering. Thousands of nodes can verify in parallel.

Simpler double-spend prevention. Once a UTXO is consumed, it's removed from the set. Trying to spend it twice is detected by "that UTXO doesn't exist anymore." No need for account-level locking or sequencing.

Composability. A transaction can consume 5 UTXOs and produce 3, or consume 1 and produce 100. There's no "split" or "merge" operation — just inputs and outputs. Lightning, atomic swaps, multi-party contracts — they all build on this primitive.

Privacy. Each UTXO can be sent to a fresh address. There's no permanent "account" people can watch. (Imperfect — chain analysis can often link addresses — but the foundation is set up for it.)

Account-balance chains (Ethereum, most others) made the opposite tradeoff: simpler programming model, more expressive smart contracts, but global state that has to be carefully sequenced and locked.

So when a wallet UI shows "Balance: 2.5 BTC", it's the wallet doing arithmetic on UTXOs the user controls. Bitcoin itself doesn't know about Alice. It knows about UTXO abc123:0 (locked to a specific hash), UTXO def456:1 (locked to a different hash), and so on. Alice happens to have the private keys that can sign for both.

This is also why **UTXO selection is a real subfield**: which UTXOs should a wallet pick when you want to send X BTC? Smallest first (avoids leaving "dust")? Largest first (fewer inputs, smaller tx, lower fee)? Minimize change? Privacy-aware (don't combine UTXOs from different addresses, since that links them)? Every serious wallet has its own algorithm.

The simulator uses a balance model because tracking UTXOs would 5× the wallet complexity for limited educational gain at this level. But every real Bitcoin wallet, every block explorer, every Lightning node, every exchange's hot wallet — they're all built around the UTXO set.

📦
On a real bitcoind, run bitcoin-cli listunspent to see your wallet's actual UTXO list. That's what gets selected from when you call sendtoaddress.
07

Transactions and the mempool

A transaction moves bitcoin from one address to another. To create one, you sign it with the private key controlling the source address (proving you have the authority to spend), then broadcast it to the network.

Transactions don't immediately become part of the chain. They first sit in every node's mempool — a waiting room of unconfirmed transactions. Miners pick from the mempool when assembling the next block they're trying to mine. Higher-fee transactions get picked first, which is how fees actually work — they're the bid in an auction for limited block space.

Once a block containing your transaction is mined, your transaction has 1 confirmation. As more blocks build on top, confirmations increase. The convention is to wait ~6 confirmations before treating large payments as final — chapter 9 explains why.

08

The Merkle tree

A block can hold thousands of transactions. The header is only 80 bytes. So the header doesn't contain the transactions themselves — it contains a single 32-byte fingerprint that summarizes all of them: the merkle root.

Construction: take all the transaction IDs. Pair them up and hash each pair. Pair up those hashes and hash again. Repeat until one hash remains. That's the root.

root
H(AB)
H(CD)
tx A
tx B
tx C
tx D

Why this is clever: if you want to prove a specific transaction is in a block, you don't need the whole block. You just need the transaction itself plus log₂(N) hashes along the branch up to the root — a "merkle proof". That's how phone wallets verify payments without downloading the full chain.

🌳
Open any non-genesis block in the Block Explorer to see a real merkle tree built from that block's transactions.
09

Consensus — the longest chain wins

What if two miners find valid blocks at almost the same time? Half the network sees one first, half sees the other. Now there are two competing candidate "tips" — a temporary fork.

The rule: nodes always extend the chain with the most accumulated proof-of-work (in practice, usually the longer one). Whichever fork the next miner extends becomes the winner. The losing block becomes an orphan — its transactions go back to the mempool to be re-mined into a future block.

This is why we wait for confirmations. If your transaction is in a block that ends up on the losing fork, it's effectively undone. After 6 blocks, the chance of a reorg deep enough to reverse it is statistically negligible (assuming honest miners control most of the hashing power).

Add it all up: hashes link blocks, mining makes new blocks expensive to produce, the longest valid chain is the truth, and you can't quietly change the past without redoing all the work since. That's Bitcoin.

01

Get a wallet

A "wallet" doesn't actually hold your bitcoin — your bitcoin lives on the blockchain. The wallet holds the private keys that prove you can spend specific UTXOs (chapter 5–6 of the tutorial). It also gives you a UI to receive, send, and track payments. That's all it is: a key manager with friendly buttons.

Categories, ranked roughly from easiest to most secure:

  • Custodial apps — Cash App, Strike, Coinbase, Wallet of Satoshi. Easy onboarding, but the company holds your keys. They can freeze, lose, or seize the funds. Fine for spending money, not for savings. "Not your keys, not your coins."
  • Mobile non-custodial wallets — Phoenix, Muun, BlueWallet, Sparrow Mobile. You hold the keys (in your phone's secure storage). Good for small amounts and daily use.
  • Desktop wallets — Sparrow, Electrum, Bitcoin Core's built-in wallet. More features (PSBT signing, coin control, hardware integration) but tied to one machine.
  • Hardware wallets — Coldcard, BitBox, Ledger, Trezor. The private key is generated and stored on a dedicated chip, never touches an internet-connected device. Gold standard for serious holdings.

Recommendation for starting out: a non-custodial mobile wallet for amounts under a few hundred dollars, a hardware wallet for anything more. Avoid custodial-only setups long-term — the whole point of Bitcoin is self-custody.

02

Back up your seed phrase

When you create a non-custodial wallet, it generates a seed phrase: 12 or 24 English words. This phrase deterministically derives every private key the wallet will ever produce (BIP39 + BIP32). Whoever has the seed has the money. Period.

Rules — these are not negotiable:

  • Write it down on paper. Or punch it into stainless steel (Cryptosteel, Steelwallet) for fire/flood protection. Never store it digitally — no photos, no cloud notes, no password manager, no email to yourself.
  • Never share it with anyone. No "support agent" will ever legitimately ask for it. If someone does, it's a scam. Always.
  • Store it somewhere safe and findable. Lost paper = lost coins. Heir-readable copies in a fireproof safe is the typical setup.
  • Test recovery before you deposit serious money. Wipe the wallet, restore from the seed, confirm the same addresses appear. If recovery fails, find out now, not when you've already loaded $50k onto it.

This is the single most common way people lose Bitcoin: bad seed backup. Not hacking, not mining attacks — just losing the paper or never writing it down. The protocol is mathematically secure; the human side is not.

📝
The simulator's wallet doesn't have a seed (no real keys), but real wallets do. Practice the discipline before you have to: write 12 random words on paper today, type them back tomorrow, see how easy it is to fumble.
03

Acquire your first sats

One bitcoin (BTC) is divisible into 100 million satoshis ("sats"). You don't need to buy a whole BTC; you can buy $5 worth.

Three main acquisition paths:

  • Bitcoin-only exchange. River, Strike, Swan, Bull Bitcoin. Verify your identity (KYC), link a bank account, buy. Withdraw to your wallet. Bitcoin-only services tend to be more reputable than altcoin-heavy ones.
  • Multi-coin exchange. Kraken, Coinbase, Gemini. Same flow, but they list dozens of coins. Functional, mainstream, also KYC.
  • Peer-to-peer (P2P). Bisq, Robosats, Hodl Hodl, Peach. No KYC, more privacy, more friction. You match with another individual; trades are escrowed in a multisig contract until both sides confirm. Slower, but no exchange holds your coins or your data.

The critical step everyone skips: after buying, withdraw to your own wallet. Bitcoin sitting on an exchange is not yours — it's an IOU from the exchange. Exchanges go bust regularly (Mt. Gox, FTX, Celsius, BlockFi). The first thing to do after buying is move it to an address whose private key you control.

04

Receive a payment

To receive bitcoin, you give the sender an address. Most wallets generate a fresh address every time you tap "Receive" — this is for privacy. (If you reuse one address, anyone watching the chain can see your full payment history at that address.)

The flow:

  1. Open your wallet, tap Receive.
  2. The wallet displays a bc1q… address and a QR code (and optionally a Lightning invoice).
  3. Send the address/QR to the payer (text, email, NFC, scan).
  4. The payer broadcasts a transaction paying that address.
  5. Within seconds, your wallet shows it as unconfirmed (it's in the mempool).
  6. After 1–6 blocks (~10–60 minutes), the payment is confirmed.

For small amounts, 1 confirmation is fine. For large amounts (tens of thousands of dollars), wait for 3–6. For payments where you're handing over an irreversible good (real estate, a car), wait longer.

⬇
Practice in the Wallet tab: click + getnewaddress to generate one, then send to it from another address (or use the dropdown on the Send form). Mine a block to confirm.
05

Send a payment

Sending is the inverse:

  1. Tap Send. Paste the recipient's address (or scan their QR).
  2. Enter the amount (in BTC or sats).
  3. Choose a fee — most wallets show "fast / medium / slow" estimates based on current mempool conditions (next block / ~30 min / ~1 hour). High fee = next block; low fee = could wait a long time if mempool is congested.
  4. Review and confirm. The wallet selects which UTXOs to consume, builds the transaction, signs it with your private key, and broadcasts it to the network.
  5. It appears in mempool within seconds, in a block within minutes (assuming a reasonable fee).

Triple-check the address before confirming. Bitcoin addresses are not human-readable. A typo sends your money to nowhere — there's no recall, no chargeback, no dispute. Sophisticated malware is known to swap copy-pasted addresses with attacker addresses (called "clipboard hijacking"); checking the first/last few characters before sending is good practice.

⬆
Practice in the Wallet tab's Send form. Pick a "from" and "to" address, set an amount, click Send. Watch it land in the mempool, then mine a block to confirm.
06

Track your transaction

Every Bitcoin transaction is public. You can look up any transaction or any address on a block explorer — a website that indexes the blockchain.

  • mempool.space — the most useful explorer for active payments. Shows your tx's mempool position, current fee market, expected confirmation time, RBF status.
  • blockstream.info — clean explorer, also has a Tor onion service for privacy.
  • Your own node — most private option (no third party sees what you're querying). See the Setup Guide.

You can search by:

  • Transaction ID (txid) — a 64-char hex string. The wallet that sent or received gives you this.
  • Address — see all txs paid to or from that address.
  • Block hash or height — see what's inside a specific block.
🔎
Practice in the Block Explorer tab — click any block to see its full structure (header, merkle root, transactions). The same information mempool.space shows for real Bitcoin.
07

Manage fees and stuck transactions

Bitcoin fees are paid in sats per virtual byte (sat/vB). Block space is finite (~1 MB / 4 MWU per block, every ~10 min); when more transactions want in than space allows, it's an auction. Your fee is your bid.

Typical mempool conditions:

  • Quiet (1–5 sat/vB) — almost everything confirms in the next block. Most weekends.
  • Normal (10–30 sat/vB) — confirms in 1–3 blocks.
  • Congested (50–500+ sat/vB) — bid wars during ordinals/inscriptions hype, ETF launches, big macro events. Low-fee txs can wait days.

If your transaction is stuck (low fee, mempool got congested after you broadcast):

  • RBF (Replace-By-Fee, BIP125) — if your wallet enabled RBF when sending, you can rebroadcast the same tx with a higher fee. Only the sender can do this.
  • CPFP (Child-Pays-For-Parent) — the recipient creates a new transaction spending the unconfirmed output, with a fee high enough to make miners include both. Useful when RBF wasn't enabled.

Modern wallets handle RBF automatically. mempool.space has a "fee bump" estimator.

08

Long-term storage

For amounts you don't move often, take security up a notch:

  • Hardware wallet (single-sig). Coldcard, BitBox, Trezor, Ledger. Private key generated and stored offline. Transactions are signed on the device — your computer never sees the key. Plug in only to sign; otherwise it sits in a drawer. Good baseline for $1k–$100k.
  • Multisig (2-of-3 or 3-of-5). Requires multiple devices/keys to sign. Lose one key → still recoverable. Compromise one device → funds still safe. Used for serious holdings, family inheritance setups, treasury management. Tools: Sparrow, Specter, Nunchuk, Casa, Unchained.
  • Air-gapped setups. Sign transactions on a device that has never connected to the internet. Coordinate via QR codes or microSD cards. Maximum paranoia mode.

The general principle: cold storage means private keys never touch an internet-connected device. The more you have, the colder it should be.

Going further

Once the basics are routine, here's what's worth exploring next:

  • Run your own node. Don't trust anyone's blockchain data — verify it yourself. Bitcoin Core, Umbrel, Start9, MyNode, Raspiblitz make this approachable on a Raspberry Pi or old laptop. See the Setup Guide for the development version (regtest); same software, different network flag for mainnet.
  • Lightning Network. Bitcoin's layer-2 for instant, cheap (sub-cent) payments. Open a payment channel, transact off-chain at unlimited speed, settle on-chain when you close. Phoenix and Muun are the easiest mobile entry points; LND, CLN, and Eclair are the serious node implementations.
  • Privacy tools. CoinJoin (JoinMarket, Whirlpool, Wabisabi) breaks transaction graph analysis. Lightning + Tor for payment privacy. Coin control in your wallet to avoid linking UTXOs.
  • Build something. PSBT-based workflows, descriptor wallets, miniscript contracts, BTCPay Server for accepting payments, Lightning APIs for in-app payments. The Setup Guide + the RPC Console are your starting points for development.
  • Read the source. Bitcoin Core is ~150k lines of well-documented C++ at github.com/bitcoin/bitcoin. The consensus rules in validation.cpp and script/interpreter.cpp are the actual rules of the network. Surprisingly readable.

Bitcoin is a deep rabbit hole. The basics fit in this guide; the rest is decades of work — cryptography, distributed systems, monetary theory, game theory, hardware engineering. Pick a thread that interests you and pull.

Simulator vs. real regtest — when to use which

The web app you're using right now teaches the mechanics. Real Bitcoin Core in regtest mode lets you build software against the actual protocol. Different goals — pick based on what you want to do next.

The natural path: get comfortable with the concepts here, then if you're going further, follow the steps below to set up the real thing. Anything you build against real regtest works identically on mainnet — same C++, same consensus rules, just a different chain ID and a difficulty floor. That's the whole point of regtest.

Step 1 · Install Bitcoin Core

Get it from bitcoincore.org. Verify signatures if you care. On Debian/Ubuntu:

$ sudo apt install bitcoind

You only need bitcoind (daemon) and bitcoin-cli (RPC client). The bitcoin-qt GUI is optional and not useful for regtest.

Step 2 · Config file

Create ~/.bitcoin/bitcoin.conf (Linux/Mac) or %APPDATA%\Bitcoin\bitcoin.conf (Windows):

regtest=1 server=1 rpcuser=test rpcpassword=test fallbackfee=0.0002 [regtest] rpcport=18443

fallbackfee is needed because regtest has no fee market and the wallet would otherwise refuse to send. Credentials are local-only so test/test is fine.

Step 3 · Start the daemon

$ bitcoind -regtest -daemon Bitcoin Core starting

Logs go to ~/.bitcoin/regtest/debug.log if you want to watch.

Step 4 · Wallet & address

$ bitcoin-cli -regtest createwallet "playground" $ ADDR=$(bitcoin-cli -regtest getnewaddress) $ echo $ADDR bcrt1qw508d6qejxtdg4y5r3zarvary0c5xw7kygt080

The bcrt1q… prefix is regtest's equivalent of bc1 on mainnet.

Step 5 · Mine your first 101 blocks

$ bitcoin-cli -regtest generatetoaddress 101 $ADDR $ bitcoin-cli -regtest getbalance 50.00000000

Why 101? Coinbase rewards need 100 confirmations to mature. 101 blocks = exactly one spendable reward (block 1's coinbase, with 100 blocks built on top). Subsidy starts at 50 BTC, same schedule as mainnet.

Cleanup

$ bitcoin-cli -regtest stop # wipe and restart fresh: $ rm -rf ~/.bitcoin/regtest

Regtest is sandboxed. The data directory is self-contained. Coins can't leave regtest. The chain doesn't connect to external peers by default.

Why this is the right environment for learning

You can break things on purpose without consequences. Submit a block with a bad merkle root and read the exact consensus error. Reorg the chain by spinning up two nodes and seeing the shorter one orphaned. Build a block by hand from getblocktemplate and watch submitblock accept it. None of this is possible on mainnet because the lottery framing ($) gets in the way of the mechanics. Regtest strips it back to: here is what the protocol actually does.

The candidate block above is built before mining starts: prev hash from the current chain tip, coinbase tx paying the reward to your address, merkle root from the coinbase plus any mempool transactions, and a timestamp. Mining is then purely the nonce search — every other field stays fixed. Once a valid hash is found, the block is appended to the chain and a fresh candidate (#N+2) is prepared.

For scale — Bitcoin mainnet right now (April 2026): difficulty 135.59 T, network hashrate ~940 EH/s, average block interval ~9 min 35 s. A valid mainnet block hash needs roughly 20 leading hex zeros. This simulator with 4 leading zeros is about 10²⁰ times easier — that's why your laptop finds blocks instantly here.

Reorg Demo — what "longest chain wins" actually looks like

Two miners somewhere in the world find blocks at almost the same time. The network has two competing tips. Whichever fork extends first becomes canonical; the other's blocks are orphaned and their transactions return to the mempool. Drive that scenario yourself.

How this demo works

Sandboxed — the main simulator's chain is untouched. Both Chain A and Chain B branch off a shared split point (think: the last block everyone agreed on before the network temporarily forked). Mine on either chain to extend it. When one becomes longer, click Resolve fork to apply Bitcoin's longest-chain rule: the longer side becomes the canonical chain, the shorter side's blocks become orphans.

What just happened?

In real Bitcoin, the network doesn't have a "Resolve" button — every node independently follows the longest valid chain it sees. When two valid chains exist, nodes provisionally accept whichever they saw first, but the moment they see a longer one, they switch. This is why confirmations matter: a transaction in a 1-block-deep block can be reversed if a competing 2-block fork shows up. By 6 confirmations, the chance of a deep enough reorg to reverse it is negligible (assuming honest majority hashpower).

The orphaned chain isn't lost forever — its transactions go back to the mempool to be re-mined into future blocks. The miners who found those orphan blocks lose their coinbase reward (it was never canonical). That's the cost of mining on the wrong fork.
